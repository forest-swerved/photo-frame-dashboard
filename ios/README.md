# Family Frame for iPhone and iPad

Native SwiftUI app, iOS 17+, using the same dedicated Swerved Family Frame API and household as the web dashboard and physical frame. No production credentials, family data, or APNs private keys are bundled. The interface follows the dashboard's bright Swerved light theme.

## Implemented

- School calendars select school-day or non-school-day weekly task routines automatically, while existing routines keep any-school-status behavior. Today and Tasks show the server's household-zone day classification. School days group saved tasks into Before school, After school and any-time sections; non-school days use one Tasks list. The Tasks tab keeps empty before/after sections visible for setup and offers parent add actions prefilled with the child and section. Existing routines and saved work are never assigned an inferred phase. The native calendar viewer includes coverage dates, source link, published days off and parent changes; parents with task permission can set or remove a version-checked date override. Early dismissal remains a school day. One-time tasks remain independent of school-day filters, and holidays/task breaks remain separate. Unknown calendar coverage is displayed explicitly rather than inferred locally.
- Today shows approved required-work progress separately from submitted work, plus a parent approval queue and individual task sections. Daily occurrences keep saved instructions, checklists, assignment, required/optional and approval rules. Tasks supports repeating weekday routines, one-time tasks, household-zone deadlines, reminder lead time, optional work, checklists, parent approval/return, excusing/rescheduling an occurrence, bounded history, and holiday/vacation breaks. Routine edits affect newly generated days; previous occurrences retain their definitions. Each completion/action uses the full occurrence version and a mutation ID, with monotonic merges and no automatic replay after an uncertain result.
- Shared calendar for the next two weeks, including multi-day all-day events and overnight events. A lazy agenda groups parsed dates when a snapshot changes, supports safe optional calendar names/colors and calendar filters, and shows event details with end times and overnight continuation. Empty calendar availability is confirmed only after a current-session successful read of a ready, complete, non-truncated snapshot covering the displayed dates and timezone; stale events remain visible. Unchanged events/metadata/day/timezone reuse the grouped agenda. Apple Calendar remains the editing source; calendar connection and parent invitations link to the existing web setup.
- Shared parent/child email-and-password sign-in, native account creation, emailed confirmation codes and resend, followed by an opaque mobile-session exchange. A parent creates an invitation bound to a child's real email and task profile; only that verified account can accept it.
- Timed calendar events do not generate phone push alerts; Apple Calendar handles those. The paired frame shows silent animated event reminders. The calendar notification switch controls connection-health updates only.
- School-calendar task reminders target each child at 7 AM and 4 PM on school days and 11 AM on non-school days, in the household timezone, only while actionable tasks remain. Unknown school coverage skips these reminders. Parents receive named task submissions/completions and one all-tasks-completed summary per child/day, independently of reward policy. Children can request device time with a duration and optional reason; parents approve or decline in Devices. Approval atomically queues the existing timed session and alerts the other parent and requesting child. Parent timed/all-day/Internet-on grants and confirmed earned-time starts name the parent, child and device as appropriate. Category switches, quiet hours and an alert-details privacy switch apply per account.
- Account-owned Activity/read state and notification preferences, including reward/session categories and native quiet hours. A push supplies only an opaque notification ID; navigation and task details resolve from the current account's authenticated inbox. Previous-account responses cannot open household details after sign-out. Parents can create child invitations, issue one-time shared-frame unlock codes, set explicit caregiver task/Internet permissions, and revoke mobile sessions. Children can issue a frame code only for their own profile. Codes stay in memory and disappear on leaving the page.
- Native password recovery requests an email, accepts a recovery code or complete recovery link, and sets a new password of at least 12 characters. Successful recovery clears the local credential/cache and returns to normal sign-in; server recovery revokes other sessions. The app never treats recovery proof as a household/mobile session.
- Devices and Internet time: server-confirmed task credits offer Use now / Save for later and a single-device picker. Parents can make timed or all-day allowances, pause/resume/end sessions, add or remove time, edit reward/daily/bedtime/carryover policies, maintain a device inventory and review activity. Network controls require a fresh authenticated snapshot and a verified integration/device; unconfigured and pilot-required states remain explicit. Optional Apple notification transport can be kept available for phones/tablets, with its shared-app scope explained. Ambiguous starts reserve their credit until the network confirms the outcome; review credits require a reasoned parent restore/consume decision.
- Countdown display uses an authenticated server-time anchor plus a monotonic clock. Queued timed starts/resumes with no assigned deadline show reserved time without consuming it or claiming access. Confirmed timed pauses save the remainder; all-day windows retain their household-midnight deadline, including a long daylight-saving day. The app never enforces a network deadline or infers that a provider blocked access from a zero countdown. Pending/unknown states stay visible; network/session revisions reject old reads, stale editors and account-switch replies, without replaying writes.
- Permanent account deletion is available from Settings and from verified unlinked onboarding, with current-password reauthentication, exact-text confirmation and a final destructive confirmation. A successful response clears local access; an uncertain response does not claim deletion. Existing adult caregivers can receive ownership through an explicit parent-admin transfer and role refresh. Privacy links are available before sign-in and in Settings.
- iOS notification permission, APNs registration delegate, stable installation UUID in Keychain, authenticated token registration, separate sandbox/production configuration, and server-readiness status. Registration and permission are shown separately from server configuration.
- Pull-to-refresh and foreground refresh coalesce invalidations into one flight plus a trailing read. Independent calendar/Activity work does not disable current version-checked tasks. Preferences and service readiness load initially and on explicit Settings refresh. Late responses cannot restore another account's state or replace newer saved preferences. Cached data remains read-only until the household refresh succeeds; reads started before an uncertain mutation cannot clear its review state. Confirmed completion versions merge monotonically and row feedback ends at acknowledgment. Conflicts are never automatically overwritten or replayed with a newer version.
- Localized due times, due-soon/overdue labels, native quiet-hour time pickers, Dynamic Type, VoiceOver headings/selected filters, and at least 44-point primary row controls. Account fields scroll into view when the keyboard opens. Only supported notification categories appear for a child account.

## Open and build

`FamilyFrame.xcodeproj` is checked in. No Swift package or other third-party runtime dependencies are required. `project.yml` is the source for regenerating the project with XcodeGen when adding files or changing project settings.

```sh
open ios/FamilyFrame.xcodeproj
```

The checked public configuration is `Config/FamilyFrame.xcconfig`:

- Bundle ID: `com.swerved.familyframe` (confirm availability under the selected Apple Developer team; the backend's Swerved account does not determine the signing team).
- API host: `forest-family-frame.vercel.app`.
- No development team is selected. Add the actual team in Xcode's Signing & Capabilities or an ignored `Config/Local.xcconfig` containing `DEVELOPMENT_TEAM = <your team ID>`.
- Debug requests the APNs `development` entitlement and sends `sandbox`; Release requests `production`. Build settings alone do not prove the signed result: an archive can be development-signed despite its Release configuration. Verify that the exported app's code entitlements, embedded provisioning profile, and `FamilyAPNSEnvironment` agree. Ad hoc and TestFlight distribution use production APNs; development-signed builds use the `development` entitlement and send `sandbox`.

A simulator build does not need a signing team:

```sh
cd ios
xcodebuild -project FamilyFrame.xcodeproj -scheme FamilyFrame \
  -destination 'generic/platform=iOS Simulator' \
  -derivedDataPath build/DerivedData CODE_SIGNING_ALLOWED=NO build
```

Run the model and client-contract tests on an available simulator (substitute its actual ID from `xcrun simctl list devices available`):

```sh
xcodebuild -project FamilyFrame.xcodeproj -scheme FamilyFrame \
  -destination 'platform=iOS Simulator,id=<SIMULATOR_UUID>' \
  -parallel-testing-enabled NO -collect-test-diagnostics never \
  -derivedDataPath build/SignedSimulator CODE_SIGN_IDENTITY=- test
```

Use local ad-hoc simulator signing (`CODE_SIGN_IDENTITY=-`) for the tests: Keychain integration tests need an application identity even though they do not require an Apple Developer team.

To regenerate the project after editing `project.yml`, run `xcodegen generate` from this folder. Regenerate the original vector app icon with `swift scripts/make-app-icon.swift FamilyFrame/Assets.xcassets/AppIcon.appiconset/AppIcon.png` on macOS.

## Authentication and local protection

Account onboarding uses a memory-only URLSession cookie store for the gateway's email/password or signup/confirmation → `/api/auth/token` → optional `/api/join` → `/api/mobile/sessions` sequence. Redirects are refused, requests stay on the configured HTTPS origin, and login cookies are cleared after the mobile exchange succeeds or onboarding is canceled. An account awaiting email confirmation or a household invitation retains only that ephemeral in-memory cookie jar. Passwords and provider JWTs are never written to app storage. Subsequent requests use `Authorization: FamilyMobile <opaque token>` and the canonical Origin. Parents create email/profile-bound child invitations through `/api/invites` with role `child`, the chosen `personId`, and the child's actual email. The child signs in or signs up with their own email, confirms it, and accepts the invitation through `/api/join`. The server verifies the authoritative confirmed email and derives the mobile role/profile; the client never assigns its own privileges. Accounts without household membership remain in Join your family and receive no mobile credential. The UI shows a child only their own assigned tasks. Anonymous child code pairing is retired; the physical frame's pairing remains separate.

The mobile credential and current session metadata use Keychain `WhenUnlockedThisDeviceOnly`. The installation UUID has its own Keychain item; it survives local sign-out so server token registration remains tied to the same installation. If the server explicitly returns `installation_conflict`, the app rotates the Keychain installation UUID and retries registration once; other errors are not silently retried. No secrets use UserDefaults. Cached data is scoped to the authenticated principal, written atomically with complete file protection, and excluded from device backups. Sign-out clears the credential and cache, requests server revocation, and removes delivered notifications. If revocation cannot reach the server, the app explicitly reports that only local sign-out is confirmed. App-switcher snapshots are covered when the scene is inactive.

Offline data is for reading. The app does not queue background mutations or infer that a timed-out write failed. It pauses changes after an uncertain response and asks the user to refresh before trying again. This avoids silently marking the wrong occurrence or forcing an old state over another family member's update.

## Account management and release checks

Account creation, recovery and deletion initiation are implemented. The deletion route reauthenticates the current password and verifies the account email on the server. Ownership transfer and network cleanup can block household deletion with an actionable server message; shared family history may remain anonymized. A verified account whose membership was already cleaned up can retry deletion from onboarding without joining another family. Local tests never delete a real account or transfer real household ownership. Before external review, independently qualify the deployed fulfillment path with isolated reviewer accounts/data and verify the privacy policy, retention behavior and metadata. [Apple's account deletion guidance](https://developer.apple.com/support/offering-account-deletion-in-your-app/).

## Signing and distribution

A simulator build and tests do **not** establish distribution or push delivery. Use the intended Apple Developer team, enable Push Notifications, and provision the chosen bundle ID. Keep APNs authentication keys and their Key ID / Team ID / topic only in the server environment; never add a `.p8` file to the app, Git, or an xcconfig. Follow the backend's documented environment names for separate sandbox and production keys, and configure the server scheduler. App Settings reads `/api/mobile/status` to show server readiness separately from device permission and registration.

- **Private registered-device installation:** export the archive with Xcode's `release-testing` method for ad hoc distribution. Every intended iPhone/iPad UDID must be registered and included in the exported app's provisioning profile. Verify the exported signature and matching production APNs configuration before installing; installing the raw archive is not equivalent. This route does not establish TestFlight availability.
- **TestFlight:** create the App Store Connect app record, validate and upload the distribution build, complete app/privacy/export metadata, and request external beta review. Qualify deployed account-deletion fulfillment, the privacy policy and its in-app link, accurate export-compliance declarations, and isolated reviewer access/data before external review. Invite family testers after approval. TestFlight builds expire after 90 days; continued household use needs maintained releases or another approved distribution route.

On physical iPhones/iPads, verify parent/child signup, email delivery/confirmation, email-bound invitation acceptance, sign-in, permissions, each enabled notification category, notification-open refresh, quiet hours, token rotation, device revocation, and closed-app receipt. Server acceptance, device delivery, and the person reading an alert are separate proof states.

Alerts are standard UserNotifications alerts. Named details (including request reasons) appear in alerts by default; turn off “Show family details in alerts” to use generic private lock-screen text. Navigation still uses only an opaque notification ID resolved through the authenticated Activity inbox. The app does not bypass Focus or use Critical Alerts. APNs and iOS are best-effort, so exact alarm-clock delivery times cannot be guaranteed. Scheduled due/overdue work runs on the server, not in unreliable iOS background timers.

Official references: [APNs registration](https://developer.apple.com/documentation/usernotifications/registering-your-app-with-apns), [notification permission](https://developer.apple.com/documentation/usernotifications/asking-permission-to-use-notifications), [APNs server authentication](https://developer.apple.com/documentation/usernotifications/establishing-a-token-based-connection-to-apns), [sending APNs requests](https://developer.apple.com/documentation/usernotifications/sending-notification-requests-to-apns), [background-push limits](https://developer.apple.com/documentation/usernotifications/pushing-background-updates-to-your-app), [TestFlight](https://developer.apple.com/help/app-store-connect/test-a-beta-version/testflight-overview/), [current App Store SDK floor](https://developer.apple.com/news/upcoming-requirements/?id=04282026a).
